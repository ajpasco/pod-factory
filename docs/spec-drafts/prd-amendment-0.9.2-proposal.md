# Proposed PRD amendment 0.9.1 to 0.9.2: sixteen rewordings across twelve requirements and section 2

> Applied 2026-10-13 as PRD 0.9.2 by amendment record 0004, together with the approver's scope changes of that day (parallel builders after phase 1b, environments, asynchronous revocation, no automatic merging in milestone zero). Kept for the audit trail.

For the approver's wording approval (ADR-010 item 6). Each row quotes the current criterion in `docs/PRD.md` section 4 and proposes a replacement that names what is observable. Rows 1 to 12 state criteria in terms the eval plan can test, as the PRD's section 4 introduction requires before gate 2; rows 4, 6, 8, 9 and 12 narrow a guarantee to what is observable, and the approver should read them as such. Rows 13 to 16 carry two changes the approver initiated on 2026-10-12 (ADR-012 section D): the parallel inline option and per-phase test locking. Applying it reopens gate 1 only for the requirements listed, and the gate-1 record stays valid for the other twelve.

| # | Requirement | Current wording | Proposed wording |
|---|---|---|---|
| 1 | REQ-02 | "proposes no refactoring" | "proposes only additions to the project rules; a proposal to change existing code is flagged as out of scope" |
| 2 | REQ-04 | "a design question about something the PRD settles is rejected" | "a decision record that both cites a settling clause and records a question put to you is rejected; which clauses settle a question is reviewed, not measured" |
| 3 | REQ-04 and REQ-10 | "a fresh-context technical review" / "written by a fresh-context agent" | "a technical review (or packet) whose recorded inputs are exactly the inputs named for that role and whose agent session started for that task" |
| 4 | REQ-08 | "Builder context is exactly what the orchestrator supplied and is recorded" | "The inputs the orchestrator supplies to a builder are recorded with their hashes and limited to the story file, the spec sections and mockup screenshots it lists, and the project rules; what a builder reads afterwards with its own tools is outside the record until sandboxes exist" |
| 5 | REQ-08 | "Killing the builder, the orchestrator or Orca at any point and restarting loses no record" | "Killing the builder, the orchestrator or Orca at each defined kill point (after every record write, between steps, during a record write, during a push) and restarting loses no record and duplicates none" |
| 6 | REQ-13 | "A dispatched builder cannot open a question prompt the orchestrator cannot see" | "Under Claude Code, a dispatched builder's attempt to open the local question tool is denied and pointed at the orchestrator's ask command; other agents are held by instruction only" |
| 7 | REQ-16 | "the whole workflow runs with Claude Code alone" | "the whole workflow runs with Claude Code alone, demonstrated by the scripted flow in CI and by the live milestone-zero run" |
| 8 | REQ-18 and REQ-21 | "Credentials never appear in any log, artifact or model context" / "never appear in any transcript, log or artifact" | "Planted canary credentials appear in none of the transcripts, logs, artifacts, records, reports or executor output produced by the scripted story and release runs" |
| 9 | REQ-22 | "every failure that stops work produces a plain-language message with your options" | "each of the nine catalogued stop points (refused approval, blocked merge, parked story, halted release, failed rollback, lease expiry, invalid record, a hook denial that stops a builder, a failing doctor) and any unexpected crash produce a plain-language message with your options, checked by the plain-language lint, with the raw error kept in the log" |
| 10 | REQ-12 | "the approving process is never an agent" | "the approving process refuses to run from a known agent session and runs only from a human-owned shell; an agent forging a record as your user is the accepted limitation in section 5" |
| 11 | REQ-13 | "Between orchestrator and human, no default is ever taken" | "The needs-human flag clears only through your answer record; no timeout and no agent action clears it" |
| 12 | REQ-21 | "Declared secret files are unreadable to agents" | "Agent reads of declared secret files through file tools are denied; shell reads are denied by an advisory heuristic; the canary tests are the proof" |
| 13 | Section 2, "Build and verify" (decision 2) | "In Orca, stories run in parallel under supervision; without Orca, they run one at a time in a single session." | "In Orca, stories run in parallel under supervision; without Orca, they run in a single session, one at a time by default, or in parallel when the approved build plan marks them independent. Every builder works in its own worktree." (approver's direction, ADR-003) |
| 14 | Section 2, gate 2 | "Tests are run and classified before approval to demonstrate missing behavior while preserving existing regression baselines." | "Tests are run and classified before the approval that locks them, to demonstrate missing behavior while preserving existing regression baselines: phase zero's and milestone zero's tests at gate 2, and each later phase's before that phase's build plan, as human-written amendments to the lock." (answer A5, ADR-010 item 5) |
| 15 | REQ-05 | "Before approval each test is classified: new-behavior tests fail for the expected reason, negative tests are paired with the positive operation they guard and the pair demonstrates the missing behavior, existing tests keep their baseline; anything else blocks approval by name." | "Before the approval that locks it, each test is classified: new-behavior tests fail for the expected reason, negative tests are paired with the positive operation they guard and the pair demonstrates the missing behavior, existing tests keep their baseline; anything else blocks that approval by name." (only the opening clause changes; the rules stay whole) |
| 16 | REQ-06 | "The lock covers the tests, the eval plan, runner configuration, fixtures, the exact test command, lockfiles, smoke tests, runbook scripts and the enforcement code." | Same sentence, followed by: "Tests arrive per phase; each phase's tests join the lock through a human-written amendment before that phase's build plan." |
