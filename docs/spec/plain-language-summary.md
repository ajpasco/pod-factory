# pod-factory: the design in plain language

For your gate 2 approval. An agent that took no part in drafting the design wrote this from the final documents of 2026-10-12. The approved requirements, version 0.9.1, govern. Where a later decision overrides an earlier one, this summary describes the later one. Gate 2 is open: no gate-2 approval and no lock exist yet.

## 1. What is being built

pod-factory is an open-source workflow for building production-ready software with AI agents (models that write code), where the rules are enforced, not just stated. Every project passes five gates (points needing human approval): requirements, design and tests, build plan, code review, and release. Only a person can approve a gate, through a plain-language command that refuses to run for an agent. Between gates, agents work under rules that programs check rather than trust. It works with nothing but Claude Code (Anthropic's coding agent tool). Inside Orca (a workspace for agents) it adds parallel agents, a board (columns showing each stage) and a control room (one screen for oversight). The first project built this way is pod-factory itself, under a declared exception that lets its first pieces be written and approved by hand until its first release. The second, an application that is not pod-factory, is not chosen yet.

The documents hold thirteen decision records (one per significant decision) and a test plan of 230 tests: 107 positive tests, showing something works, and 123 negative tests (attempts that must fail). They map 157 acceptance criteria (observable conditions for done) across 24 requirements. They name seven enforcement layers (where rules get checked) and eighteen platform assumptions (untested facts about tools) still to verify.

- Documents disagree: the design's index and the test plan's own tally still say 207 tests, and the handoff (a briefing written for you) says 223.
- Documents disagree: the handoff still speaks of twelve decision records.
- Documents disagree: the eleventh decision record's opening, the tally in the criterion table (links criteria to controls) and the handoff's account of that record say seventeen assumptions. The list itself and the latest record give eighteen.
- Documents disagree: the proposed amendment to the requirements counts twelve requirements and one section in its title and closing list, as does the latest decision record. Its rows reword eleven, as the twelfth decision record and the handoff say.

Version one arrives in seven phases:

- Phase 0, the scaffold (the hand-built first pieces). It covers approving and rejecting, locking files so agents cannot change them, and the store of records (files proving who decided). It adds the first hooks (Claude Code's pre-action checks) and automated checks, and a minimal health check (reports every layer's state). It also adds the first commands for stories (one requirement's work unit) and a tool that moves the early records into place. Bootstrap records (hand-written early approvals) approve these pieces.
- Phase 1a: milestone zero, described below.
- Phase 1b: the rest of gates 1 to 4. That means the interview, discovery (mapping existing code first) and mockups (clickable, throwaway fake screens), then the reviewers, guided design, checking tests before approval, delegation, the full verify step and the one-command install. Release 0.1 ships at its end through a manual runbook (the scripted release steps), which ends the exception. Its place before Orca is yours to confirm.
- Phase 2: the Orca backend (running stories through Orca): supervised parallel builders (agents writing code), the board, and fixes sent back to the same builder.
- Phase 3: gate 5 and the release program (non-AI software that deploys).
- Phase 4: the control room, metrics and the retrospective (a post-release look back).
- Phase 5: managed setup for founders, which configures git (the version history tool), GitHub (the code hosting service), the automated checks, protections, hooks and the password store.

**The first usable milestone** is milestone zero: one story, end to end, in a single Claude Code session. The story is the status report, which prints every story, its stage, its owner and what it waits on. It must pass through requirements, locked tests, building, evidence and a merge (accepting a change permanently) that you approve. It must survive the session being killed at any point. Three refusals must be seen working. An agent's change to a locked test is denied, and the automated checks reject it too. A change made after your code-review approval is refused at merge until it is reviewed again. A "tests passed" claim with no test output tied to the exact content is rejected.

## 2. How a project flows, as you experience it

**Start.** You answer an interview, one question at a time: what the product does, for whom, the stack (the technologies it uses), where it runs, and who is on the project. Product questions cannot be skipped. Technical questions come with a recommended default, and a default you accept is recorded as one. A preflight, the health check run before installing, names each enforcement layer as present or missing. No application code can be created until gate 1 is approved. If the project already has code, discovery comes first. It reports conventions, measured test coverage (share of code tested), risky areas, vulnerable dependencies (outside code it uses) and proposed rules, and you approve it before any design.

**Gate 1, requirements.** An agent drafts the requirements, each with its user, its flow and its acceptance criteria. Anything with screens gets a mockup with made-up data, and you click through every flow. Four reviewers who start with no history argue against the document: a skeptical founder, a security reviewer, an operations engineer and a feasibility reviewer. Every finding is fixed, deferred, or dismissed with a reason you acknowledge. To approve, you type the gate number and the first eight characters of a fingerprint (unique to exact content) that the command shows you. The approval binds each requirement and the mockup. Editing either reopens the gate.

**Gate 2, design and tests: this approval.** The design is built by asking you one question per significant decision the requirements left open, with a recommended option and its consequence. Anything already settled is cited, not asked. The design covers phases, interfaces (how the parts connect), non-goals (what is deliberately excluded) and budgets. It also covers a threat review (how attacks are resisted) and production readiness (operating and releasing safely), including the runbook, plus the criterion table. The test plan turns each criterion into positive and negative tests. A fresh agent (one with no history) retells each test in plain English from its code, and you acknowledge every one. Before you approve, the tests run once and are classified (checked to fail correctly). Each new test must fail for its stated reason, since nothing is built yet, and existing tests must still pass. Anything else blocks approval by name. Then the tests and everything they depend on are locked.

**Gate 3, build plan.** The orchestrator (the coordinating AI agent) splits the design into stories. Each is full stack (from screen to storage) and lists its tests, interfaces, the files it may touch, budgets, caps (limits on repeat rounds), and the agent and model assigned. A fresh reviewer checks the plan for gaps. The approval packet (what you approve from) estimates tokens (units of model usage) and days. No builder starts before your approval exists.

**Build and verify.** Each builder works in its own copy of the project. It sees only its story, the design sections the story names, the project rules and the mockup screenshots. It holds no credentials (passwords and access keys). It writes the least code that passes the locked tests and leaves a handoff note for whoever continues. Before anything reaches you, checks run. Every new file must trace to a requirement, and no code may go untested. Size and complexity tripwires (flags without stopping work) apply. Scans look for secrets and vulnerable dependencies. A security review, a simplicity review and testing as a user follow, with evidence. Bugs go back to the builder that made them. Builders' questions go to the orchestrator, which answers only what the documents settle, quoting the sentence, and brings everything else to you. The story then waits; no default is ever taken.

**Gate 4, code review.** A fresh agent writes the review packet from the final content. It holds a plain-language summary, the requirements covered, test evidence, every finding, any delegated decisions, screenshots of screens, and four closing lines. Engineers also get the diff (the exact line changes). You approve, or reject with reasons. Merge is blocked without your approval tied to that exact content, and any later change needs a new review. Gate 4 is the only gate you can delegate, in writing; even then, the merge waits for your acknowledgment.

**Gate 5, release.** The release is built and verified first, and its rollback (restoring the previous release) is rehearsed. A checklist carries evidence for every item, including the security condition: every story's scans and security review complete, no unresolved blocking finding, and every exception shown as a waiver (a visible time-limited exception). You sign off on the release and its rollback together. A release agent then asks the release program to deploy exactly that build. Only the program holds the credentials.

**Throughout.** State lives in files, so any session can be killed and restarted. Approvals, locks and decisions are records that you or a checked process produce; agents cannot write them. Stories move through draft, ready, in progress, verifying, in review and done, and can be flagged as parked or needing you. Inside Orca, the board's columns are those stages; without Orca, the status report is the view. Desktop notifications, an optional web notification and Orca, when present, tell you when something needs you. Every failure that stops work gives you a plain-language message with your options. Metrics count issues caught per gate, bugs that reached production (from incidents you record), rework, and elapsed time and tokens per story, all computed offline. Nothing measures how you review or approve. After each release, a retrospective asks one optional question and proposes rule changes for you to approve.

## 3. The significant decisions

**How it installs and runs.** Version one is one package on npm (JavaScript's public package registry). One command installs it on a computer that already has Node (the JavaScript runtime engine), in its current or previous long-term-support release. The same program serves you, the hooks, the automated checks and the release program, and it ships an exact list of the outside code it uses. The Claude Code plugin (an installable add-on package) adds hooks and commands once per machine. The skills (instruction packs for agents) install with one command. Both install from a fixed release, never from unreleased work. Downloads with Node built in come with managed setup, the last phase. The names were free on 2026-10-12 but are not reserved yet. *For you:* until managed setup arrives, an engineer must install it; a founder alone cannot.

**One repository.** Everything lives in one repository (where the project lives): the command-line program (you type its commands), hooks, checks, release program, skills, templates, both plugins and the documents. The Orca plugin is published from its own branch (a separate history line), because Orca's installer needs the plugin's description file at the top level. *For you:* one version number and one place to report problems, at the cost of one extra release step that the health check verifies.

**Without Orca, and with it.** Without Orca, the orchestrator runs in your Claude Code session. It starts each builder, tester and reviewer as a fresh helper agent with only the context it needs. Stories run one at a time by default, or in parallel when the approved plan marks them independent: no shared interface, no overlapping files, no dependency. In every mode, each builder works in its own worktree (a separate working copy) and registers it as its first step, so the hooks can tell builders from the orchestrator. A builder that skips this gains nothing: its work is rejected and the story returns to ready. Merges back to the main line (the project's official history) happen one at a time. With Orca, the same four actions (start a story, wait for it, send a fix to the same builder, ask you) run on Orca's supervised workers, used only when Orca answers a status check. Orca shows and carries the work but never enforces. Telling builders apart assumes a hook sees the builder's own copy; phase zero checks this, and a failure is reported, not hidden. *For you:* the whole workflow runs with Claude Code alone, and the parallel option without Orca, your own direction, changes an approved decision whose new wording is in the proposed amendment.

**Where approvals and records live.** Every approval, lock, amendment, waiver, decision and check result is a small readable file, one per record, on a dedicated records branch. There are fourteen kinds. Each names what it binds by fingerprint, who wrote it, when, and the versions in force. People write theirs only through thirteen human-only commands, which refuse to run for an agent; the checking program writes check results, stage changes and delegated decisions. Keeping records apart from the code means an approval is written the moment it is given, with no code review in between, and no change to the code can alter one. The records branch only grows: nothing on it is edited or deleted, and a later record changes an earlier one's effect. A job defined on the main line checks new records every few minutes. Only checked records count for gates, merges and releases; an invalid one is flagged and never counts. Test evidence sits on a companion branch, listed by fingerprint, so metrics and the audit view (every record, who, when) work offline. *For you:* your approval can take a few minutes to count for a merge or release, while routine work never waits.

**How the rules are enforced.** Seven layers hold the rules. Two run on your machine: the hooks and a pre-commit check (runs before saving changes). Five live on GitHub: automated checks defined on the main line, protection of the main line, protection of the records branch, code owners (required reviewers for files), and required checks (checks that must pass) for each kind of change. The machine layers are fast but can be bypassed; GitHub's layers decide. A hook decides alone only where nothing else sees the act: an edit before saving, a read, a question, a builder starting. A hook that cannot decide blocks writes to locked, protected and secret files and allows the rest. Because the deciding checks are defined on the main line, a change cannot rewrite its own judge, and checks that run proposed code cannot write records. **One guard runs on every change to the main line:** the lock guard fails any change to a locked file that lacks your amendment tied to that exact content. Beside it, a class check sorts each change into exactly one kind: story, work area and documents, locked files, rules, release, and in phase zero only, bootstrap. It fails a change that fits no kind or strays outside its allowed files. Work-area and document changes then merge on their own once checks pass, since nothing there binds until a record does. Version one ships check settings for GitHub only. *For you:* the health check is itself a required check, and it fails while any layer is missing or waived.

- Documents disagree: the criterion table still names the story check as what blocks locked-file changes; the latest decision record gives that job to the lock guard, and the table is due to be regenerated.

**How tests are locked, and when.** Right after your gate-2 approval, the lock is written. It covers the tests and their prepared data, the test plan, the test settings and the seven exact test commands. It also covers the dependency lists, the release smoke tests (quick post-release checks) and scripts, and the code that enforces the rules. The automated checks run the locked commands, never a version a change brings along. Changing anything locked takes your written amendment; for a test, you first acknowledge its before-and-after plain-English readings. Even adding a dependency is an amendment. Tests are written per phase: phase zero's and milestone zero's before gate 2 closes, and each later phase's before that phase's build plan, added by amendment with their classification. Builders may add small tests of their own; these stay unlocked, and the simplicity review flags any that test nothing that matters. *For you:* the requirements say every test is locked at gate 2; per-phase locking was your answer, and its wording change is in the proposed amendment.

**Budgets and the three modes.** Each story starts with generous defaults: 5,000,000 tokens, 8 hours, 3 fix rounds and 2 re-reviews, plus 3 reopenings per build plan. Tripwires sit at 10 files, 400 changed lines, a nesting depth of 3 and a complexity score of 10, two measures of tangled code. In hard-stop mode, the default, a cost, time or repeat-round overrun parks the story and asks you; size overruns only flag. In tripwire mode, every overrun flags and needs a written reason; nothing parks. In off mode, nothing is enforced or flagged; estimates and usage are still recorded, and every packet and status view says budgets are off. Only your amendment changes the mode; an agent's edit is ignored and flagged. Milestone zero measures real usage, and the first retrospective proposes new defaults. *For you:* off mode, which you added, means you watch spending yourself.

**Releases and credentials.** When a release change merges, the automated checks build the package once from that exact revision (an exact saved version). They record its fingerprint and run the regression tests (tests guarding existing behavior) and a rollback rehearsal against it. You then sign off, binding the revision, the build's fingerprint, the environment (where it is deployed), the configuration, data migrations (changes to stored data), the runbook and the rollback plan. The release program runs on your machine. Before step one, it re-checks every bound input and halts on any mismatch; it never rebuilds. Credentials live only in the system password store or the 1Password manager, typed at a hidden prompt (input never displayed). The program hands each one only to the step that needs it, masks it in all output, and never shows it to the release agent, which can only request steps. A smoke test that cannot run is retried, then halts for you, and never triggers a rollback. A failure confirmed by a re-check triggers the pre-approved rollback at once, without you. Any other recovery waits for you. Release 0.1 ships before this program exists, through a manual runbook run from your terminal. *For you:* releases run from your machine, where the credentials live; a cloud-hosted release program is a later option.

**Stacks.** Two ready-made stacks and a custom path. The web default is a Python service built with FastAPI, a React web front end in TypeScript (JavaScript with type checks) and a Postgres database. Docker (repeatable packaged app environments) runs it locally, and its code follows a plain layered structure with no speculative abstractions. The node-tool stack is TypeScript on Node for command-line tools, libraries and services; pod-factory itself uses it. Each comes with project rules, a folder layout, the test command the lock will pin, security basics and the check wiring. For any other stack, the start step recommends one with a one-line reason, asks you, and writes rules on the fly. Those are reviewed at gate 2, not pre-tested, and must declare where application code lives before gate 1. *For you:* the two named stacks start from tested rules; anything else relies on review.

## 4. Blocked, measured, or only reviewed

The design ties each of the 157 criteria to one kind of control: 46 are blocked, 108 are measured and recorded, 2 are only reviewed, and 1 waits for the proposed amendment. The automated checks and GitHub's rules decide 66 of them, the factory's own programs 83, hooks 5 and agent review 2; the last one has no deciding layer yet.

**Blocked: something refuses and work stops.**
- Before design: skipping a product question, or application code before gate 1. A gate-1 approval with a missing layer and no waiver, or a user flow with no mockup screen. Design before discovery is approved, or without a matching gate-1 approval.
- At any gate: an undecided finding, an unacknowledged dismissal or plain-English reading, a misclassified test, or a design with no technical review when no engineer is on the project. Withdrawing an approval reopens its gate.
- Locks: an agent's edit to a locked file, and any change to one without your amendment.
- Building: a builder starting without your checked build plan, a story starting before it is ready, or a change outside the story's files. In hard-stop mode, a cost, time or repeat-round overrun parks the story.
- Before code review: a failing check, an open blocking security finding, or user testing without evidence.
- Merging: without your approval tied to the exact content, after any later change, under delegation without your acknowledgment, or for rule changes you have not approved. Delegating any gate but gate 4, or acting on authority no written policy grants, is refused.
- Releasing: signing off before the build exists and is verified, or starting with any input that differs from the sign-off. Also a rebuild that differs, a rollback when a check merely failed to run, any other recovery without you, and credentials entered other than at the hidden prompt or from a password store.
- Always: a builder opening its own question prompt, an agent reading a declared secret file, and a needs-you flag clearing without your answer.

**Measured and recorded: a program produces a result tied to exact content.**
- What every approval, lock, amendment, waiver and withdrawal binds, checked by the records job.
- Each test's classification before approval, and the locked tests' results, with evidence tied to the content tested.
- Untraced code listed by file, fixes routed to the original builder, and the budget mode shown everywhere.
- Secrets masked before anything is written, and canaries (planted fake secret values) absent from every scripted run's output.
- The packet's sections, its four closing lines, and a plain-language check on its summary.
- Metrics, the health check, the status report, the event log and the audit view.
- Recovery after a killed session, and each release step's smoke result and rollback.

**Only reviewed: a recorded judgment, never proof.**
- Whether a discovery report proposes refactoring, and whether a design question asked something the requirements already settle.
- Beyond the criteria, every reviewer's verdict, from the gate-1 reviewers to security, simplicity and user testing, records attention, not correctness. A passing AI behavior test means only that its defined scenarios passed.

Answering a builder from the approved documents needs no delegation: the orchestrator records the answer with the sentence it quotes. Deciding a question the documents leave open does: it needs a category you granted in a written policy. Without one, the decision is refused, logged as a question that should have been asked, and brought to you.

## 5. What version one does not defend against

**Accepted risks.**
- An agent deliberately forging your approval while running as your computer user. Version one guards against drift and mistakes, not malice. Optional signatures are checked when you set up a signing key.
- Builders are separated by good practice, not walls. They share your user account, the project's history, your own credentials and an open network, so a rogue one could still query your password store. They get no deployment credentials, cannot edit protected files with their tools, and changes outside their files fail the automated checks. Sandboxes (sealed spaces per story) come in version two.
- Builders may read files beyond what they were given; such reads are logged, not blocked. No network limits apply to any agent.
- Hooks exist only for Claude Code. Other agents, such as Codex (another vendor's coding agent), meet only the pre-commit check, the automated checks and GitHub's rules.
- The hook that reads shell commands uses a heuristic (a rule of thumb), not a guarantee. Shell reads of secret files are blocked only that way; the canary tests are the proof.
- Secrets outside the supported channels and declared files are protected only by masking patterns.
- Private repositories on GitHub's free plan lack its protection rules, so they run under a visible waiver or upgrade the plan.
- Orca's multi-agent features are experimental and never enforce anything.

**Deferred to version two or later.** Per-story sandboxes and approvals that need a physical action. Hooks for Codex are a candidate. Also deferred: monitoring AI features in production, mutation testing (testing the tests themselves) and feature flags (switches turning features on) beyond a recipe. So are a hosted or multi-user service, sync with work trackers such as Jira and Linear, the control room on remote machines, high-fidelity design tools and a rich Orca side panel. Check settings beyond GitHub and stacks beyond the three wait too. Provisioning hosting or cloud accounts is out of scope.

## 7. Closing lines

- **What this design changes:** It turns the approved requirements into seven phases, thirteen decision records, a criterion table and a 230-test plan, and proposes fourteen rewordings of the requirements. It openly changes approved decisions: the parallel option without Orca, per-phase test locking, and finishing gates 1 to 4 before Orca, which is yours to confirm. It also settles technical defaults on a project with an engineer, an approach you authorized; each stays open to overrule.
- **What was checked while writing it:** A full verification pass found one blocker, eleven major and thirteen minor issues, and seven places where the design touched an approved decision without saying so. A second pass checked the corrections. The last two decision records resolve both, except the two items left to you, and every open item the drafts raised is resolved in a decision record. For this summary, every number was recounted from the documents as they stand.
- **What remains uncertain:** Eighteen platform assumptions are unverified; nine are checked in phase zero. The largest: that GitHub runs the scheduled record checks reliably, and counts checks defined on the main line as required. The budgets are starting points until milestone zero measures real usage. Only the security and simplicity reviewers have scenario tests; the other reviewers' judgment is reviewed by you, not measured. Some documents still carry older counts.
- **What approving it authorizes:** Binding the requirements at their current fingerprint, version 0.9.2 if you approve the amendment. With them it binds the criterion table, the design, the test plan, the runbook narrative and step file, and the rollback plan; there is no mockup, since pod-factory has no interactive screens. Your approval lets the first tests and placeholder code past the lock guard, then the lock is written over the tests and everything they depend on, and the technical defaults stand unless you overrule them. No builder starts until you approve a build plan at gate 3.
