## The five corrections, and what each changed

1. **The unlocked test location already exists**, so nothing needs inventing and `LOCKED_PATTERNS` does not change. The locked runner configuration collects `test/**/*.test.ts` and `src/**/*.test.ts`; the lock covers `packages/*/test/**` and not the source tree; and `packages/*/vitest.config.ts` is itself locked, so a builder may add a test beside the code it tests inside its story's approved scope while no agent can widen the set the runner collects. Story one's brief already grants exactly this for `*.test.ts` under `src/status/`. The first draft's claim that milestone zero had no unlocked location was wrong and ADR-016 item 10 now says so.
2. **A small reference application**, not the status page, carries the criteria a CLI cannot exercise. One database-backed journey through an approved mockup, sign-in, a list and a detail view one role may edit and another may only read, each screen's loading, empty and error states, and the production checks the contract names; one journey, two roles, one table, nothing further. It is the second project PRD section 3 named, which resolves open question 2, and the phase-1b exit now states which project exercises which gate 1 to 4 criterion.
3. **Review evidence lives outside the tree it reviews.** The first draft had the reviewer commit its review into the pull request, which changes the tree and so invalidates the exact-tree binding by the act of recording it — the same circularity as the gate-2 classification report, which this project had already written down once. It now reuses the evidence path `verify` uses: a review bundle outside the checkout whose manifest names the pull request, head commit and head tree, uploaded as an artifact, read as data by a job that runs no application code and writes a check result carrying the review's digest. Any application change is a new tree and needs a fresh review.
4. **The whole lifecycle, not one branch.** ADR-016 now holds "The smallest complete implementation": six changes covering the authorization binding its contract and losing its cover when that contract no longer holds, merge eligibility, the review record, story completion with no human approval, revocation reaching every dependent pull request, and post-merge verification of the combined application with progression that waits for a passing result and still allows its own repair. The first draft's "essentially one new gate-check branch" was true only of merge eligibility, and the ADR says so by name.
5. **The revision is marked as taking effect with record 0006**, in the PRD header, the tech spec header and ADR-016's status line.

## The second round: three more corrections

The approver read the corrected branch and found two rules still loose and one sentence left behind. All three are fixed here, in ADR-016 and the tech spec; `docs/PRD.md` is untouched by this round, so the hash below and the draft record stand.

6. **Post-merge verification must wait for success, not merely for the absence of failure, and must not block its own repair.** The earlier item 6 stopped progression "while the latest integration result for main is failing", which left a missing, pending or stale result unspecified — work could advance on no evidence at all, or on a result for a tree main no longer has — and, once main failed, blocked the repair too. Now: ordinary progression requires a passing result for main's current tree, and the refusal names which of failing, missing, pending or earlier-tree it hit, because those are not the same problem. Recovery is a narrow exception, one pull request while main's tree is failing: a repair inside the failing story's file scope, or a revert under a human approval record, judged on verification of the repaired content with its head taken from the failing tree, never on main as it stands. A repair that does not clear it parks the story through the loop cap the PRD already provides.
7. **The contract references need an invalidation rule, not just a reference.** Binding the gate-2 approval and the lock says what the authorization rested on; it does not say what happens when those authorities are revoked or superseded, or when the content they bound drifts. Now: an authorization covers a story only while it and every authority it names are unrevoked and that bound content still hashes as bound, the locked paths and the gate-2 files each with their valid amendments applied in order, checked when work is dispatched and again at merge; where it fails, the work waits for a fresh `approve 3` against the authorities then in force and every open pull request relying on the old one fails `gate-check` with the reason named. An approved amendment is not drift. Two consequences recorded with it: this is a different check from the file scope, which prevents a widened scope and establishes nothing about the contract still being authorized; and the relay must reach one level deeper, so revoking a lock or a gate-2 approval fails every open pull request whose authorization references it.
8. **One leftover sentence deleted.** ADR-016's last rejected alternative still read "The review is a committed file in the work zone", which contradicted correction 3 in the same document. It now says the reviewer produces the review and a job that runs no application code reads it as data and writes the check result.

Both rules are normative, so they are in `docs/TECH-SPEC.md` section 5 as well as in the ADR: after gate 2 the tech spec is bound and the ADR is not, and a rule that lives only in decision history can be edited by any agent later.

## The final two requirements, added with the approval

The approver named two more before approving, and both are incorporated: REQ-10 and the build narrative carry the first, REQ-09 carries the second, tech spec section 5 carries both as rules and section 7 carries the worker side, and ADR-016 carries the reasoning, the cost and the alternatives.

9. **Every automatic merge is of content verified and reviewed with main as it then stands.** The content judged is the merge candidate, not a head that predates main: the merge base must be main's current head, so the head tree is the tree the merge leaves, and when main moves the candidate is stale, the branch is refreshed, and verify and the review run again. REQ-10's existing rule that a content change after a review requires a new review is what makes the second review mandatory. This is the one place the design leans on a protection setting: `gate-check` checks the merge base itself, but main can still move between that run and the merge, so the up-to-date setting is required protection on a repository running the authorization path, where the locked-path rule treats it only as a backstop (ADR-015), and `doctor` checks it. It also generalises the recovery rule the second round added: a repair's head taken from the failing tree is this requirement applied to that case. The cost is recorded: in phase 2 merges serialise and every candidate behind one merge refreshes, re-verifies and is reviewed again.
10. **A failing integration result must not trap the work that can fix it.** The story whose merge produced the failing main tree can be resumed for a bounded repair by the worker that built it, even when that story is already done, while everything unrelated stays blocked. It needs no new stage: done to in progress becomes a legal transition exactly when the latest integration result for main's current tree is failing and names that story, and nothing else reopens a done story. The resumption path and the fourth dispatch verb already exist; the bounds are the story's approved file scope, the loop cap, and the rule that a repair needing a path outside that scope, or a second repair that leaves the failure in place, is the human's. It is item 7 of ADR-016's implementation plan, which is now seven changes rather than six. Rejected with it: opening a new story for the repair, because a new story is outside the authorized plan and would need a human record, which is the interruption this direction removes.

## What is not in this branch, on purpose

Nothing that enables automatic merging, which is also the approver's own condition on the approval: it stays disabled until phase 1b's implementation passes its acceptance tests. `gate-check` still requires a human approval record bound to the head tree, exactly as on main. Authorized execution is phase-1b work, described in tech spec section 5 and ADR-016 as a design, not as shipped behavior. Milestone zero's own rules are unchanged: three required checks, a human approval for every pull request, one builder at a time, and story one's merge is the approver's.

The later-phase parts of `docs/spec/*.md` and `docs/eval-plan.md` still describe per-story approval and the pull-request classes. They are subordinate reference under tech spec section 13 and are revised by phase 1b's own classification amendment. Rewriting them now would cost an amendment against the lock for text no phase has reached.
