Version 1.1, 2026-10-14. Status: **gate 2 open; this revision takes effect with PRD amendment record 0006 and governs nothing until that record exists.** Governed by `docs/PRD.md`: 0.9.2 as approved (gate-1 record 0001, amendments 0002 and 0004), and 0.10 once record 0006 is written. - Engineer on the project: yes (the approver). No user interface in version one beyond the CLI and a generated status page. ## 3. Milestone zero

### 3.1 Scope

**Commands.** `approve <gate|story|bootstrap|amendment>`, `lock`, `revoke <record>`, `story start`, `story finish`, `status`, `doctor`, `hook`, `ci <job>`. Nothing else.

**Records.** approval, lock, revocation, status transition, check result. One schema, five record types.

**CI jobs, all defined on main and all required on every pull request:** `lock-guard`, `verify`, `gate-check`; plus `records-validate` on a schedule and on demand. No branch classes and no automatic merging: every pull request to main needs the approver's approval record bound to its tree.

**Stages.** ready, in progress, verifying, done. "Needs human" is a flag `status` shows.

**Hook.** One: deny agent file edits to locked and protected paths. The approval-path commands refuse to run from an agent session by environment marker, and CI rejects a human record whose writer is not human.

### 3.2 What each piece does

- `approve` shows the artifact's hash and a plain-language line, asks the human to type the gate and the first eight characters of the hash, writes the approval record, pushes it. It is idempotent: when a valid, unrevoked approval already carries the same shown hash it writes nothing, so a restart after a kill never approves the same content twice; `lock`, `story start` and `story finish` are likewise safe to run again. `approve story-<n>` binds the story branch's head tree; in milestone zero that one approval is both the story's merge authority and acceptance of a one-story product, which phase 1b separates. `approve bootstrap <pull request>` is the merge authority before the first lock exists. `approve amendment <paths>` authorizes a change to locked paths by binding before and after hashes.
- `lock` writes the lock record from the approved eval plan: the locked patterns, every matching path with its hash, the approved tree, and the exact test commands in order, starting with the install line.
- `revoke` writes a revocation record, triggers `records-validate` at once, and reports **pending** until CI confirms that every affected open pull request shows a failing gate-check; only then does it report enforced. It takes a record ID or a bootstrap record's file name and a `--reason`, shows a statement and a hash to type back as `approve` does, and waits up to `--wait` seconds (120 by default) for the relay; running it again for a revoked record reports the state without writing, and while enforcement is still pending it triggers `records-validate` again, so a run stopped after the revocation landed but before the trigger is completed by running it again. The affected pull request comes from the records alone: the one a revoked story, bootstrap or amendment approval or verify result names, when its open head's tree is the tree that record binds. A revocation only withdraws authority, with one exception: revoking a lock unlocks its paths, so the confirmation names every path that stops being locked before the hash is typed. Revoking the gate-2 approval reopens gate 2 and leaves the lock in force until a new gate-2 approval and lock.
- `story start` requires a valid gate-3 approval for the current plan, writes the in-progress transition with a lease, and prints the builder's inputs with hashes. `story finish` writes the verifying transition after the builder's handoff note is recorded. A story file carries three labelled lists the commands read, `Tests:`, `Scope:` and `Inputs:`, each a `- <path or glob>` per line; the rest is prose for the builder. `story start story-<n> --holder <builder>` may be run by the orchestrator (an agent): it refuses unless every file the gate-3 approval binds still hashes the same on main and every path under `Tests:` is locked at its current hash, and when the story is already in progress it writes nothing and reprints the lease and inputs. `story finish story-<n> --pr <n>` moves in-progress to verifying when `.factory/work/story-<n>/handoff.md` is on the pull request's head, and verifying to done when a valid story approval for that pull request binds its head and that content is merged: the approved head is in main's history, or main holds exactly the approved tree (a squash); the command says which held. `story finish` exits non-zero only when something is wrong, and reports with exit 0, writing nothing, whenever it is waiting on someone else: no story approval yet, or approved and not yet merged. A pull request that changed after its approval is wrong, not waiting, and is refused.
- `status` prints every story, its stage, what it waits on, and the exact rule or record blocking it. It is the tool for "what went wrong."
- `doctor` reports each enforcement layer present or missing: the plugin hook, the CI workflows on main, main's branch protection including administrators, the records branch protection, required checks configured. In milestone zero: main's `.claude/settings.json` runs hook 1 exactly as shipped; `pod-factory` resolves on PATH to a real copy outside any git checkout; main has `pr-checks.yml` with its four jobs on `pull_request_target` and `records-validate.yml` scheduled with the relay; main binds administrators, forbids force pushes and deletion, and requires `lock-guard`, `verify` and `gate-check` from the GitHub Actions app (`strict` is reported, not required, and a still-required `bootstrap-check` is named as the placeholder); the records branch exists with nothing flagged, forbids force pushes and deletion, and requires no checks or reviews, which would stop `verify-record` pushing. A layer it cannot check counts as missing. It is read-only and runs from any session. It proves the binary is a real copy outside any checkout, not that it is the newest one: the package version does not change in milestone zero and nothing records the source commit in the build.
- Every `ci` job runs from the enforcing copy, main's code at the commit the `pull_request_target` event names, and prints that commit; the pull request's head is fetched as data. The enforcing version is "bootstrap until release 0.1" (section 1), which is main's enforcement code as merged under approvals.
- `ci lock-guard`: applies the locked-path rule (ADR-015), which judges what a merge would leave on main, path by path. A locked path the pull request changes between the merge base and the head passes when its head content is exactly what is locked now, or when a valid, unrevoked amendment approval bound to this pull request and its head tree approves that content. A locked path it leaves alone is what the merge keeps from main, so main's content there must be content this lock has approved: the lock's own, or an applied amendment's. The two halves differ on purpose, and ADR-015 names what each prevents. The rule does not depend on branches being up to date with main. The locked hashes are the lock's with each valid, unrevoked amendment applied in order; `approve amendment` takes its before hashes from the same function. `ci verify`: runs the locked command exactly as locked in a job that holds a read-only token and passes no token to the code it runs, uploads the evidence bundle; a second job, `verify-record`, runs no application code and writes the check-result record with the bundle's manifest hash, taking the verdict from the verify job's own conclusion as well as the bundle. `ci gate-check`: requires an approval record bound to this exact head tree, a passing verify for this tree and no revocation of either, and the locked-path rule holding, evaluated against the records branch as it is at that moment; it reads the branch again before reporting and evaluates again if it moved. gate-check evaluates the locked-path rule itself, through the same function lock-guard uses and against the records it read, and deliberately depends on neither lock-guard's check run nor any lock-guard record: a re-run supersedes a GitHub check run, so a green lock-guard run proves nothing after a revocation, and lock-guard writes no record. For merging, lock-guard's own check run is therefore advisory and gate-check is the authority. When the change to a locked path was authorized by an amendment that has since been revoked, the failure names the amendment and the revocation. For a story approval it also checks the file scope: the diff from the merge base with main to the head stays inside the `Scope:` globs of the story file as the gate-3 approval bound it (read from that approval's tree and checked against its hash), plus `.factory/work/story-<n>/**`; anything else under `.factory/` fails. The story comes from the human's story approval, never from the branch name, which the pull request's author chooses. `ci records-validate`: validates every record on the branch per record, rejects nothing after the fact, flags invalid ones, and posts a failing gate-check on every open pull request that relied on a revoked record.

### 3.3 The flow

1. Scaffold and the gate-2 tests land through bootstrap pull requests, each under `approve bootstrap`. Branch protection with the required checks and administrator enforcement is set by hand and confirmed by `doctor`.
2. The gate-2 tests run once. Scaffold behavior passes as baselines; story-one tests fail on assertions because `status` does not exist. No placeholder code.
3. `approve 2` binds the main tree, the PRD, the design, the eval plan, the mapping and the classification output; `lock` follows at once. In milestone zero the bound files are fixed in the command: `docs/PRD.md`, `docs/TECH-SPEC.md`, every `docs/spec/*.md` (the design sections, including `docs/spec/criterion-to-control-mapping.md`), `docs/eval-plan.md` and the classification report `.factory/work/classification/gate-2.json`; `docs/adr/` is history and is not bound. `--classification` names the bootstrap classification record, which must bind that report's hash. `lock-guard` is live from here.
4. `approve 3` on the one-story build plan. `story start`. A builder subagent in its own worktree implements `status` against the locked tests and writes its handoff note. `story finish`.
5. The pull request runs `lock-guard`, `verify` and `gate-check`; gate-check fails until the approver acts.
6. The approver reads the evidence bundle and the diff, runs `approve story-1`, re-runs gate-check, merges.
7. Recovery and the refusals: kill at each record write and restart from records alone; edit a locked test; approve then push one more commit; claim "tests passed" with no bundle.

### 3.4 What waits

Everything in phases 1b to 5. In milestone zero every question goes to the approver, there is no delegation, no waiver, no class, no auto-merge, no Orca, no release automation, no environment manager. Authorized execution, the recorded code review and the acceptance packet are phase 1b: milestone zero keeps the per-pull-request approval deliberately, because the approval path is what it exists to prove.

## 4. Records

- **Store.** Branch `pod-factory/records`, linear, never force-pushed, protected. One JSON file per record, `<utc-timestamp>-<type>-<subject>-<id>.json`, UTF-8, LF, two-space indent, fixed key order. Common fields: schema version, record type, factory version, hash algorithm (SHA-256 over LF-normalized UTF-8), created at, actor (name, email, kind human, check-runner or agent; agent is allowed on transition records only), binds, outcome, refs. `refs` and, from slice 5, `revocation.revokes` name a record by its 12-hex ID or a bootstrap record by its file name under `records/bootstrap/`. A lock record holds `lock.patterns` (the locked globs, so a file added under one is a change) and `lock.testCommands` (ordered, the install line first); its `binds.files` holds every matched path and `binds.tree` the approved tree.
- **IDs and retries.** The ID is generated once per command invocation and written to a local journal before the first push. A retry after a failed or uncertain push fetches first; if the ID is already on the branch the command reports success; otherwise it pushes again. Concurrent writers never conflict: each record is its own file, and a rejected push rebases and retries.
- **Validity at point of use.** Every consumer, `gate-check`, `lock-guard`, `status`, the hook, validates each record it reads: schema, writer rule for its type, hashes. An invalid record is ignored and flagged, never blocks a later valid one, and is never repaired in place. There is no validated pointer. `records-validate` is the alerting job and the revocation relay, not a gate.
- **Writers.** Human records (approval, lock, revocation) through the human commands; status transitions through the story commands; check results through CI's record-writing job. CI rejects a human record whose actor is not human. At commit level, every reader also flags a human record (approval, lock, revocation, bootstrap) committed by the Actions bot, and a check result committed by anyone else; anyone holding push rights to the records branch can forge a committer, the accepted limit of PRD section 5. Readers fetch the records branch with its full history and refuse a history a shallow clone cut short. "Latest" and "in order" mean in the order records were added to the branch, never file-name order, which ties within one second.
- **Bootstrap records** keep their field names under schema `bootstrap-0` (record types approval, amendment and classification) and live under `records/bootstrap/` on the records branch: 0001 to 0004 move there when it is created, the gate-2 classification record 0005 is added by hand before `approve 2`, and the PRD amendment 0006 is added in the working tree and on the branch with the change it binds, the classification keeping 0005 because that file name is a fixture in six test files. The exception ends at release 0.1.
- **Branch creation.** The approver creates `pod-factory/records` by hand, once, after slice 2 lands and before slice 3 makes gate-check required; its root commit holds the four bootstrap records under `records/bootstrap/`, and the CLI never creates the branch.

## 5. Merge rules

Milestone zero: three required checks on every pull request, `lock-guard`, `verify`, `gate-check`; merge needs the approver's approval record bound to the head tree. Main's protection binds administrators; `doctor` checks it. A direct push by an agent holding the approver's credentials is the accepted risk of PRD section 5.

Phase 1b replaces the per-story human approval with authorized execution, and drops the pull-request classes and `class-check` that ADR-012 to ADR-014 proposed: the required set stays `lock-guard`, `verify`, `gate-check`. `gate-check` passes an implementation pull request when a valid, unrevoked gate-3 authorization covers the story, a passing verify binds the content being merged, a closed review result with no open blocking finding binds that same content, the diff stays inside the story's approved file scope, and the locked-path rule holds. On that path the content being merged is the merge candidate including main as it stands, so the pull request's merge base must be main's current head and both results must bind that head tree; when main moves the candidate is stale, and the branch is refreshed and verify and the review run again before it may merge. This is the one place the design requires branches to be up to date: `gate-check` checks the merge base itself, and because main can still move between the last check and the merge, GitHub's up-to-date setting is required protection on a repository running the authorization path rather than the backstop it is for the locked-path rule (ADR-015), and `doctor` checks it. A human approval bound to the head tree remains an alternative path, and is the only path for anything outside an authorized story's scope; there the approver binds the tree they read, and the post-merge verification below is what catches a skew that binding cannot see. An authorization covers a story only while it and every authority it references are unrevoked and the content those authorities bound still hashes as bound, the locked paths and the gate-2 files each at their approved hashes with their valid amendments applied in order; this holds when work is dispatched and again at merge, and where it fails the work waits for a fresh gate-3 authorization against the authorities then in force.

The combined application is verified on main's own tree after every merge, and ordinary progression requires a passing result for main's current tree: a failing, missing, pending or earlier-tree result stops dispatch and merge. Two things still move while main's tree is failing, and nothing else does. A repair inside the failing story's file scope, or a revert under a human approval record, may merge on verification of the repaired content, with its head taken from the failing tree. And the story whose merge produced that tree may be resumed for that repair by the worker that built it, through the fourth dispatch verb of section 7, which needs no new stage: done to in progress is a legal transition exactly when the latest integration result for main's current tree is failing and names that story, and nothing else reopens a done story. A repair that needs a path outside the story's scope, or that leaves the failure in place a second time, is the human's.

Changing the contract still takes a human record: an amendment, or a new gate approval. The authorization path is in force nowhere until its own acceptance tests pass: milestone zero, and every project until phase 1b's implementation is verified, keep the per-story human approval. The class rules in `docs/spec/interfaces-and-non-goals.md` and ADR-012 to ADR-014 are superseded history and are built in no phase.

## 6. Revocation

A revocation is effective on the records branch the moment it lands. `revoke` triggers `records-validate` immediately and falls back to the schedule. `records-validate` posts a failing `gate-check` on every open pull request whose approval it revoked, and records each block as a failing gate-check check result naming the revocation, which is what `revoke` reads to report enforced. Every `gate-check` run evaluates the records branch at its own start time and refuses to report a pass if a newer records-branch commit revoked anything it relied on, so a stale run cannot restore an obsolete green. Until CI confirms the block, `revoke` and `status` show the revocation as **pending**. A merge completed before the revocation stands as history and is undone by a revert pull request under its own approval. Revoking an amendment whose pull request already merged fails every pull request that leaves those paths alone, until a pull request restores them to what is locked now, which needs no amendment, or an amendment approves what main holds (ADR-015).

## 7. Builders

- Each builder runs in its own git worktree with its own test data, started as a Claude Code subagent with worktree isolation. The orchestrator records the inputs it supplies with their hashes. The authoritative dispatch is the in-progress transition record; a local untracked pointer at the worktree root serves status and resumption.
- Each session's handoff note is `.factory/work/<story or bootstrap slice>/handoff.md`, in the work zone.
- Milestone zero and phase 1b: one builder at a time.
- Phase 2: independent stories in parallel, two builders at a time by default. The approved plan names dependencies and the stories that may run together; shared foundations come first; stories with overlapping files, conflicting migrations or unfinished shared interfaces run sequentially. Changes merge one at a time and the combined application is verified after each merge. Parallel builders get separate ports and test databases; with Compose, distinct project names and volumes per story; cleanup touches only that story's resources. The inline and Orca backends implement the same four verbs: start a story, wait for done, send a fix back to the same worker, ask the human.
- After a failing post-merge verification of main, the fix goes back to the worker that built the story through the same fourth verb, resumed in the worktree it used or in a fresh one at the merged commit when that worktree is gone. The repair is bounded three ways: the story's approved file scope, the loop cap, and the rule that a second failure is the human's. Reopening the story is a transition, not a new stage (section 5).
- The builder contract: a story is full stack for one requirement; the approved contract defines done, and the story's acceptance tests and its recorded review are the evidence that it is met; builder-written tests are allowed, unlocked, must test behavior that matters, and never stand in for an acceptance test. The unlocked location already exists and needs no new rule: the locked runner configuration collects `test/**/*.test.ts` and `src/**/*.test.ts`, the lock covers `packages/*/test/**` but not the source tree, and `packages/*/vitest.config.ts` is itself locked, so a builder may add a test beside the code it tests inside its story's approved scope while no agent can widen or narrow the set the runner collects. Story one's brief already grants exactly this, for `*.test.ts` under `src/status/`.

## 8. Environments

- The design selects the deployment target and the development environment. For a web application with a backend and a database it recommends Docker Compose. A simple CLI tool needs no Docker.
- Setup detects whether Docker is installed and running; prepares the Dockerfile, Compose configuration, startup commands and health checks when available; otherwise offers installation help or a supported local setup; records the chosen mode for every later agent; diagnoses a previously working environment that fails instead of silently switching.
- The local setup keeps the same application architecture, database engine, runtime versions, dependency lockfiles, migrations and configuration names as deployment. SQLite never stands in for Postgres.
- When the target is containers, CI builds and tests the deployment image even if the developer runs locally without Docker, and deployment approval binds that artifact.
- No generalized environment manager: the smallest supported paths, extended when real use requires it.

## 9. Hooks and the agent layer

Milestone zero ships hook 1: deny agent file edits to locked and protected paths, failing closed on those paths when it cannot decide. It is `pod-factory hook pre-tool-use`, configured in the project's committed `.claude/settings.json` (a locked path) and run from the `pod-factory` binary installed from main as a packed copy (`npm pack`, then `npm install -g` of the tarball; a global install of the folder is a symlink into the checkout), never a worktree's build; when the binary is missing the configured command exits 2, so every edit is refused rather than allowed. It answers Write, Edit, MultiEdit and NotebookEdit, resolving each path against the git checkout of the event's working directory (a builder's own worktree) both as written and through symlinks. Protected, always, lock or no lock: `.factory/records/**`, `.claude/settings.json`, `.claude/settings.local.json`, `.github/workflows/**` and `.github/CODEOWNERS`, the enforcement layer and the records' main copies. Locked: whatever the current lock record and its amendments say, read from the local copy of the records branch without fetching. The hook is a hygiene layer, not a boundary: an agent can still write a locked file with a shell redirect until the shell hook arrives in phase 1b, and lock-guard is the authority by design. A change to a protected path is a human act in milestone zero. Phase 1b's `amend` exists because an amendment approval binds an after hash that only exists once the change is made, so something must authorise the change first; in milestone zero that is the approver's own hands. Phase 1b adds hooks 2 to 6: shell-command heuristic for writes and secret reads, dispatch without a gate-3 approval, the question tool in a builder worktree, reads of declared secret paths, session-start orientation. Hooks are the advisory layer; CI is authoritative. Codex and other agents are held by CI and branch protection only.

## 10. Classification and locking

Tests are written per phase and classified before the approval that locks them. Implemented scaffold behavior has passing baseline tests; unimplemented story behavior has tests that fail on their assertions; nothing working is disabled to satisfy a class. The lock covers the tests, the eval plan, runner configuration, fixtures, the exact command, lockfiles, smoke tests, runbook scripts and the enforcement code; later phases' tests join it by amendment. The milestone-zero test set is `docs/eval-plan.md` section 13.

## 11. Evidence

Verification evidence is produced by the test harness or CI and bound to the tree it tested; agent prose is never evidence. Milestone zero stores bundles as CI artifacts and commits their manifest hash in the check-result record; the evidence branch with size caps arrives with phase 1b.

A recorded review is the second kind of evidence and arrives with phase 1b. It is not committed into the tree it reviews: committing it would change that tree, and a review bound to an exact tree that its own recording invalidates can never be satisfied. It reuses the evidence path `verify` already uses. The reviewer writes its findings and dispositions, with any screenshots, into a review bundle outside the checkout; the bundle's manifest names the pull request, the head commit and the head tree, as the verify bundle's does; the bundle is uploaded as a workflow artifact; and a record-writing job that runs no application code reads it as data and writes a check result carrying the review's digest and the tree reviewed. What CI checks is that a review exists for this exact tree, that its manifest matches the content under review, that it names its findings and leaves none of them open. What the reviewer found stays the reviewer's judgment, and the record says so. Any change to the application is a new tree and needs a fresh review; recording the review never changes what was reviewed. Product verification (REQ-27) adds no machinery beyond that: the journeys are tests in the locked set, the browser and operational reviews are recorded reviews, and the thresholds are numbers in the contract.
