# ADR-016: A contract approved once, execution authorized

Date: 2026-10-14. Status: **approved as a direction and as a contract, pending its record**. The approver approved the revised direction and contract on 2026-10-14 after three rounds of corrections, naming two further requirements that are incorporated here; it takes effect when he writes PRD amendment record 0006, and is in force for phase 1b onward, never for milestone zero. The PRD and tech spec revisions it describes govern nothing until that record exists, and both say so in their headers. Approving the design is not a claim that the automation is built or verified: the authorization path is in force nowhere until its own acceptance tests pass, milestone zero finishes under the per-story human approval, and the complete sequential workflow is demonstrated on the reference application before anything merges automatically. Decided by: the approver's direction of 2026-10-14, prepared by the design session. PRD basis: the promise in section 1, REQ-04 to REQ-10, REQ-13, REQ-17, REQ-26, REQ-27. Supersedes the pull-request classes in ADR-012 to ADR-014 and `docs/spec/interfaces-and-non-goals.md`.

## What changed

The promise was: a human approves at five gates, and one of them is every story's merge. The promise is now: the human approves a complete product definition and experience, authorizes agents to execute the plan that delivers it, and judges the finished product. Stories became internal execution units. The sentence that moved the most weight is in the PRD's section 1: "The approved contract defines done, and tests and recorded reviews are the evidence that it has been met." It replaces "the locked tests are the only definition of done."

This is a change of promise, not of mechanism. No new enforcement layer, no policy engine, no new document: the contract is still the PRD, the design and the eval plan; the authority is still a record only a human can write; the enforcement is still `lock-guard`, `verify` and `gate-check`.

## The approval rules this changes

1. **Merge authority.** Before: REQ-10 and tech spec section 5 blocked every merge without a human approval record bound to the story's content. After: an implementation merge proceeds with no human record when a valid, unrevoked gate-3 authorization covers the story (valid meaning that it and the authorities it references are unrevoked and the content they bound has not drifted, which the implementation section's item 1 states), every required check passes for the exact content being merged, that content's recorded review is closed with no open blocking finding, and the diff stays inside the approved file scope. The content being merged is the candidate that includes main as it stands, refreshed with its checks and its review whenever main moves, so no automatic merge rests on a result for content that is not what would land. A human approval bound to the head tree stays an alternative path, and is the only path for anything outside an authorized story's scope. **Milestone zero is exempt by design and keeps the per-pull-request approval.**
2. **Gate 4's meaning.** Before: approval of one story's code review, and the only delegable gate. After: acceptance of the product, never delegable. Still five gates, still `approve 4` as the command.
3. **Delegation narrows.** REQ-17 loses the delegated merge and its acknowledgment. Only bounded decision rights during build remain delegable; the contract, acceptance and release sign-off are not.
4. **Done.** REQ-08 and tech spec section 7: passing the locked tests is evidence, not the definition. A story is done when its part of the contract is met, which adds a closed review and a diff inside scope, and rejects behavior the contract does not carry. Done is also no longer terminal: a failing post-merge verification of main that names that story reopens it for a bounded repair inside its own scope, with no human record, and nothing else reopens a done story.
5. **What gate 2 binds.** REQ-06 binds the contract by name: requirements and scope, mockup and interaction behavior, significant architecture decisions and boundaries, acceptance criteria and test plan, production readiness criteria with their thresholds. The milestone-zero file list in tech spec section 3 step 3 does not change.
6. **Evidence admits a recorded review.** A review by a named reviewer against bound content, with its findings and dispositions, recorded by CI as a check result carrying the review's digest and the tree it reviewed. It reuses the evidence path `verify` already uses: the review goes into a bundle outside the checkout whose manifest names the pull request, head commit and head tree, the bundle is uploaded as an artifact, and a job that runs no application code reads it as data and writes the record. It is **not** committed into the tree it reviews, because that commit would change the tree and a review bound to an exact tree that its own recording invalidates can never be satisfied. CI checks that a review exists for that exact tree, that its manifest matches the content under review, that it names its findings and leaves none open. What the reviewer found stays the reviewer's judgment; an agent's claim that a check passed is still not evidence that it passed.
7. **A new condition on gate 2.** REQ-26: one review reads the PRD, the mockup and the architecture together, reports gaps by name across journeys, business rules, permissions, integrations, responsive behavior, accessibility, loading, empty and error states, and the production requirements; an open blocking finding blocks the approval.
8. **A new condition on gate 4.** REQ-27: journeys verified end to end with their failure and permission cases, a recorded browser review against the mockup, tests for business rules and boundaries, the contract's security, accessibility, performance and operational checks against its stated thresholds, and the deployment artifact exercised in its intended environment.
9. **Removed: the pull-request classes and `class-check`.** `work/*` auto-merge by branch name is gone and is built in no phase. Class membership was chosen by the branch name, which the pull request's author picks; the authorization record is the better authority, and gate-check already reads it.
10. **Agents may add tests**, in the unlocked location that already exists. The locked runner configuration collects `test/**/*.test.ts` and `src/**/*.test.ts`; the lock covers `packages/*/test/**` and not the source tree; and `packages/*/vitest.config.ts` is itself locked, so a builder may add a test beside the code it tests inside its story's approved scope while no agent can widen or narrow the set the runner collects. Story one's brief already grants exactly this for `*.test.ts` under `src/status/`. No change to `LOCKED_PATTERNS` is needed, and an earlier draft of this ADR was wrong to say milestone zero had no unlocked location.

Unchanged: who may write a human record, the lock and amendment mechanism, the locked-path rule of ADR-015, revocation and its relay, the records store, milestone zero's three required checks, and gate 5.

## What it costs

- `docs/PRD.md` is bound by bootstrap record 0004, and three milestone-zero tests enforce that binding: T-03-P5 and T-03-P7 in `packages/cli/test/bootstrap-records.test.ts` and T-06-P6 in `packages/cli/test/hash.test.ts`. T-03-P5 also asserts exactly 25 requirement IDs, and there are now 27. Changing the PRD therefore takes a new hand-written bootstrap amendment record, 0006, and those assertions updated to it; 0005 stays the gate-2 classification, whose file name is a fixture in six test files. No test title or ID changes, so `docs/eval-plan.md` section 13 and its count of sixty are untouched and the gate-2 classification stays at 167 tests, 164 passed, 3 failed.
- `approve 2` binds `docs/PRD.md` and `docs/TECH-SPEC.md`, so this change lands before the classification run or it becomes an amendment against the lock afterwards.
- The phase-1b exit now names which project exercises each gate 1 to 4 criterion, because the ones that need a user interface cannot be exercised on a CLI. The reference application carries those, and the status page is deliberately not moved forward to stand in for it: a generated read-only page would demonstrate neither a database-backed journey, nor permission cases, nor an approved mockup matched. The application is held to one journey, two roles, one table and the three screen states, and it resolves the second project that PRD section 3 named and open question 2 left open.
- Refreshing the merge candidate costs a verify and a review every time main moves under an open pull request. In phase 1b, one story at a time, that is rare and cheap. In phase 2 it is the throughput cost of the requirement: merges serialize, each merge stales every other open candidate, and the ones behind it refresh, re-verify and are reviewed again in turn. Whether that second review may be scoped to the delta main introduced is a phase-2 question and is not decided here, because REQ-10 as written requires a review of the content being merged.
- The repair path costs one transition edge, its validation and its tests, and it means a story's worktree is not discarded the moment the story is done: it is kept, or recreated at the merged commit, while main's tree has no passing result.
- The later-phase parts of `docs/spec/*.md` and `docs/eval-plan.md` still describe per-story approval and the classes. They are subordinate reference under tech spec section 13 and are revised by phase 1b's own classification amendment, not now.

## The smallest complete implementation

Seven changes, each extending something that exists. There is no new policy engine and no new framework; the authority is still a record a human wrote, and `gate-check` is still the one place that decides whether a pull request may merge. All seven are phase-1b work: milestone zero keeps its per-pull-request human approval and none of this is built for it.

1. **The authorization binds the contract it rests on, and stops covering work when that contract no longer holds.** `approve 3` today binds the build plan's tree and the hash of every story file, with `refs: []`. It gains references to the gate-2 approval and the lock record it was granted under, so an authorization can be judged against the contract in force rather than standing on its own. Those references are then checked, when work is dispatched and again at merge: an authorization covers a story only while it is itself unrevoked, every authority it names is unrevoked, and the content those authorities bound still hashes to what they bound — the locked paths at the lock's hashes with each valid, unrevoked amendment applied in order, and the gate-2 files at the hashes that approval bound, with their amendments applied the same way. So a revoked lock or gate-2 approval, a newer gate-2 approval superseding the one the authorization names, or drift in a bound file that no amendment approves, each end its cover: the affected work waits for a renewed authorization, which is a fresh `approve 3` against the authorities then in force, and every open pull request that relied on the old one fails `gate-check` with the authority and the reason named. An approved amendment is not drift, which is the point of amendments and the reason changing the PRD after gate 2 costs an amendment rather than a new authorization. This is a separate check from the file scope in item 2: reading the story file from the authorization's own tree prevents a widened scope, and establishes nothing about whether the contract that authorization rests on is still in force. Where: `commands/approve.ts` `gate3()` to write the references, `commands/story.ts` for the dispatch check, `check-runner/gate-check.ts` for the merge check.
2. **Merge eligibility.** `gate-check` gains one alternative to the per-story approval it requires today: a valid, unrevoked gate-3 authorization covering this story, a passing verify bound to the head tree, a closed review result bound to that same head tree, the file-scope check, and the locked-path rule. Four of those five already exist in `evaluate()`, and the file-scope check already reads the story file from the authorization's own tree and compares it against the hash that approval bound, so an edited story file on main cannot widen a scope. Both results must bind the merge candidate rather than a head that predates main's current state, which is one more comparison: the merge base must be main's current head, and then the head tree is the tree the merge leaves. Because main can still move between that run and the merge itself, the up-to-date setting on main's protection is required for this path and `doctor` checks it — the one place this design leans on a protection setting instead of treating it as a backstop (ADR-015). When main moves, nothing is invalidated but the candidate: the branch is refreshed, verify runs again, and the review runs again because REQ-10 already says a content change after a review requires a new review. Where: `check-runner/gate-check.ts`.
3. **The review record.** A job on the `verify-record` pattern: read the review bundle as data, check its manifest against the pull request, head commit and head tree, check that it names its findings and leaves none open, write the check result with the review's digest. Where: a new `check-runner/review-record.ts` and a job in `pr-checks.yml`.
4. **Story completion without a human approval.** `story finish` today moves a verifying story to done only when a valid story approval binds the merged head. It gains the same alternative as `gate-check`: the authorization, the closed review and the merge, with no human record. Without this change a story cannot reach done however it merged. Where: `commands/story.ts`.
5. **Revocation reaches every dependent pull request.** The relay today computes the affected pull request from the record itself, which works because a story, bootstrap or amendment approval names one pull request and binds its head tree. A gate-3 authorization names none and covers many, so revoking one must fail every open pull request whose story it covers. Where: `check-runner/records-validate.ts`, one new case in the affected-pull-request computation, reusing the block-recording path that already exists. The same case carries item 1's consequence one level deeper: revoking a lock or a gate-2 approval must fail every open pull request whose authorization references it, not only the pull requests that revoked record names.
6. **The combined application after each merge, and progression that stops without blocking its own repair.** A check on main's own tree after every merge, writing its result as a check result like any other and binding it to the tree it ran against. Ordinary progression then requires a **passing** result for main's current tree: `story start` refuses and `gate-check` fails when that result is failing, missing, still pending, or bound to an earlier tree, because a result for a tree main no longer has says nothing about main. Those states are not the same thing to the person reading the refusal, so it names which one it is and the tree it needs a result for: missing or pending waits for the check to run and the workflow can be dispatched again, while failing needs a repair.

   Recovery is a narrow exception, or the rule would block the only work that can clear it. While main's current tree has a failing result, one kind of pull request may still merge: a repair inside the file scope of the story whose merge produced that tree, or a revert, which takes a human approval record as it does today (tech spec section 6). The evidence in both cases is verification of the repaired content, never of main as it stands — the pull request's own passing `verify` and closed review bound to its head tree, with its head taken from the failing tree, so that what was verified is what the merge leaves on main. That last condition is item 2's general rule applied to this case: the candidate must include main as it stands, which for a repair means its head is taken from the failing tree. A passing result for the tree the repair produces is what reopens ordinary progression; a repair that does not clear it leaves the system where it was, and the loop cap the PRD already provides parks the story and asks the human rather than letting attempt after attempt run. `story start` already refuses when a file the authorization bound has drifted on main, so the refusal path exists and this adds reasons to use it. Where: a workflow on push to main, `check-runner/`, and `commands/story.ts`.

7. **Repair after an integration failure.** The story whose merge produced a failing main tree has to be able to carry its own repair, and today it cannot: done is terminal, in `commands/story.ts` and in the transition validation. It gains one legal edge, done to in progress, allowed exactly when the latest integration result for main's current tree is failing and names that story, and nothing else reopens a done story. The rest exists: `story start` already reprints the lease and inputs for a story that is in progress, which is the resumption path, and the fix reaches the worker that built it through the dispatch verb the design already has. The repair is bounded by the story's approved file scope, by the loop cap, and by the rule that the second failure is the human's. Where: `commands/story.ts`, `records/validate.ts` for the transition, and the dispatch side of the orchestrator.

What this replaces: the claim in an earlier draft that authorized execution was essentially one new branch in `gate-check`. That was true only of merge eligibility, item 2. Story completion, revocation reach, post-merge verification and the repair path are each their own change, and without them the lifecycle has a story that can merge but never finish, a revocation that blocks nothing, no check on the application as a whole, and no way to repair main once the check that guards it fails.

## Alternatives rejected

- **A policy engine or rules language** deciding when a merge may proceed. One more layer, and the condition is four facts gate-check already reads.
- **Keeping the classes** and giving `story/*` an auto-merge. The classes were already a cleanup dead end, and a branch name is not an authority.
- **A line-coverage threshold** as the concrete coverage number. A percentage is the metric an agent optimizes into meaninglessness; coverage is stated as named tests against named criteria, journeys, business rules and permission rules.
- **Merging gates 1 and 2** into a single contract approval. Gate 1's red team produced three amendments on this project before a design existed; merging the gates would delay the first human read of the requirements until after the design.
- **The generated status page as the subject of browser verification.** Rejected by the approver on 2026-10-14. A read-only generated page demonstrates no database-backed journey, no permission case and no mockup matched, so passing the criterion on it would be passing it on nothing. The reference application exists for that, and the status page is not moved forward to serve it.
- **Committing the review into the pull request it reviews.** Rejected: the commit changes the tree, so the review's binding to an exact tree is invalidated by the act of recording it. The same circularity as the gate-2 classification report, and it is avoided the same way, by keeping the evidence outside the content and binding it by digest.
- **Verifying GitHub's merge ref instead of requiring an updated branch.** `refs/pull/<n>/merge` already holds the merge result, so the checks could bind that tree and no branch would ever need refreshing. Rejected for now: that tree belongs to no commit on either branch, which makes "the content I reviewed" harder for a human to check out and reproduce, and GitHub recomputes the ref asynchronously when main moves, so staleness returns in a form nothing on our side can observe. It remains the obvious alternative if branch refreshes become phase 2's bottleneck.
- **Relying on the up-to-date-branches setting alone.** A setting is not a mechanism: it can be turned off and it leaves no record. `gate-check` checks the merge base itself, `doctor` checks the setting, and the setting closes only the race between the last check and the merge.
- **Opening a new story for the repair instead of reopening the one that failed.** Rejected: the authorization covers the plan's stories, so a new story would need a new human authorization, which is exactly the interruption this direction removes. Reopening keeps the repair inside the authority and the file scope that already cover that code.
- **Letting the reviewing agent write its own review record.** A record an agent writes is not a human record and must not look like one. The reviewer produces the review; a job that runs no application code reads it as data and writes the check result.
