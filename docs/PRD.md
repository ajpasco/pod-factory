# pod-factory: Product Requirements Document

Working name: **pod-factory** (CLI command and proposed repository name; the names were unregistered on 2026-10-12 and are not yet reserved). Version 0.10, 2026-10-14. Status: **the approved contract is 0.9.2 — approved at gate 1 on 0.9 (record 0001), amended to 0.9.1 by record 0002 (REQ-09 budget modes) and to 0.9.2 by record 0004 (testable criteria, parallel builders, environments, asynchronous revocation). Version 0.10, the text below, takes effect with amendment record 0006 and governs nothing until that record exists.**

This PRD governs product scope and acceptance. The reference, `docs/PRD-reference.md`, preserves prior reasoning and proposed mechanisms. The tech spec selects and justifies mechanisms consistent with this PRD and explicitly identifies any proposed change to an approved decision. Requirement IDs here match the reference and are stable; REQ-26 and REQ-27 are new at 0.10 and have no counterpart in the reference.

## 1. Who it serves and the problem it solves

People now build software with AI coding agents, and the common practice is prompt, accept, hope. The results are code nobody reviewed, tests edited until they passed, features nobody asked for, and no evidence that a requirement was met. Tools that organize this work into requirements, designs and stories exist. They stop at organization: every rule is advice an agent can ignore under pressure.

Two groups need something stronger.

- **Founders without an engineering background** need to approve what gets built and shipped in plain language, on evidence and on things they have clicked through, never on code.
- **Engineers and engineering leaders** who build through agents need their quality bar enforced instead of hoped for, with the raw diff and the command line still in reach.

pod-factory is an open-source workflow for building production-ready applications with AI agents, where the rules are enforced, not stated. It works with nothing but Claude Code, and it gains parallel agents, a board and a control room inside Orca. Other tools organize the work; this one enforces it.

**The promise.** You approve a complete product definition and experience. Agents then build a production-quality application that matches it, with appropriate architecture, engineering practices and end-to-end verification. Stories are internal execution units: you authorize the plan once and do not supervise or approve each one. The approved contract defines done, and tests and recorded reviews are the evidence that it has been met. What stays yours is the contract, the verdict on the finished product, and the decision to deploy.

## 2. The workflow, end to end

Five gates: the requirements, the build contract, authorization to execute it, acceptance of the finished product, and release. At each one a human approves before work continues, through one plain-language command that only a human can run. Between the gates, agents work under rules that are checked, not trusted. The gates are not a per-story review queue.

**Start.** You answer an interview, one question at a time: what the product does, for whom, the stack, where it runs, who is on the project. Technical questions come with a recommended default. A preflight checks that the enforcement can be installed. No application code is written before gate 1. In an existing codebase, a discovery step first maps conventions and structure, measures test coverage, flags risky areas and vulnerable dependencies, and proposes project rules; you approve that before any design.

**Gate 1, requirements.** The agent drafts the PRD: every requirement with its user, its flow and its acceptance criteria. For anything with a user interface, it builds a throwaway clickable mockup with hardcoded data and you click through every flow in Orca's browser or your own. The draft states every user journey end to end, the business rules, who may do what, the integrations the product needs, how the interface behaves at the sizes the project supports, the accessibility level it must meet, and what each screen shows while loading, when empty and on error; an unanswered journey or state is a gap, not a detail to settle later. Four fresh-context reviewers argue against the document as a skeptical founder, a security reviewer, an operations engineer and a feasibility reviewer. Every finding is fixed, deferred or dismissed with a reason you acknowledge. You approve. The approval binds the document and the mockup, and editing either reopens the gate.

**Gate 2, the build contract.** The agent designs inside what the PRD settles: it resolves ordinary technical choices itself, cites the clause for anything already decided, and brings what is left to you in one consolidated review rather than a stream of questions, each unresolved product decision and material tradeoff with a recommended option and its consequence in plain language. The design includes phases, interfaces, non-goals, budgets, a threat review and production readiness, including the release runbook, and it states the production requirements this project must meet: security, performance, configuration, migrations, observability, deployment and recovery. One review then reads the PRD, the mockup and the architecture together and reports every gap by name, in the journeys, business rules, permissions, integrations, responsive behavior, accessibility and loading, empty and error states, and in those production requirements; every blocking finding is dispositioned before you approve. The eval plan turns every acceptance criterion into positive and negative tests, shown to you as plain-English renderings that a fresh-context agent regenerates from the tests themselves. Tests are run and classified before the approval that locks them, to demonstrate missing behavior while preserving existing regression baselines: phase zero's and milestone zero's tests at gate 2, and each later phase's before that phase's build plan, as human-written amendments to the lock. The design also selects the deployment target and the development environment: for a web application with a backend and a database it recommends Docker Compose, and it never requires Docker for a simple tool. You approve. What you approve here is the build contract: the requirements and scope, the mockup and its interaction behavior, the significant architecture decisions and boundaries, the acceptance criteria and test plan, and the production readiness criteria with their thresholds. The tests, the eval plan and everything the tests depend on are locked. Agents may add their own tests where the locked runner configuration already includes them, beside the code they test and inside their story's approved scope; they cannot weaken an approved acceptance criterion to make an implementation pass, and any change to a locked path needs a human-written amendment. The contract defines done; tests and recorded reviews are the evidence that it has been met.

**Gate 3, authorization to build.** The orchestrator turns the approved contract into stories: one requirement each, with the tests to pass, the interfaces, the files it may touch, budgets, caps, and the agent and model assigned. Every story traces to an approved requirement, or to a technical dependency it names and justifies; agents add no speculative features, no unrelated refactoring and no abstraction the contract does not need. A fresh-context reviewer checks the plan for gaps. The packet shows estimated tokens and days. You approve, and that one approval authorizes the agents to execute the plan: to create the stories, implement them, review, verify, correct, hand off and progress without returning to you for each one. Nothing is dispatched before that record exists. The authority to change the contract stays separate from the authority to carry it out: no agent approves its own scope change, weakens enforcement, or widens its own authority.

**Build and verify.** Builders work in their own worktrees with only their story, the spec sections it names, the project rules and the mockup screens, and hold no credentials. They write the minimum code that meets their story's part of the contract and passes its acceptance tests, and leave a handoff note. Agents create the stories, implement them, review the code, verify it, correct what fails, hand off and move the work along; having authorized the plan, you are not asked to approve each one. Stories run one at a time by default. After milestone zero and phase 1b, independent stories may run in parallel, two builders at a time by default, in Orca under supervision or inline without it. The approved plan names dependencies and which stories may run together; shared foundations come first; stories with overlapping files, conflicting migrations or unfinished shared interfaces run one after another. Each builder has its own worktree and its own test data. Changes merge one at a time, the combined application is verified after each merge, and work waits for a passing result on main as it then stands; a failure reopens the story whose merge caused it for a bounded repair inside its own scope, by the worker that built it, and holds everything unrelated. Before anything merges, checks run: traceability of every new file and endpoint to a requirement, code no test exercises, size and complexity tripwires, secret and dependency scans, a fresh-context security review of the produced code, a simplicity review, and QA against the requirements with evidence. An implementation change merges on its own only when every required check and its recorded review pass for the exact content being merged, which is that change combined with main as it stands and is refreshed and checked again whenever main moves, the diff stays inside the story's approved file scope, and the authorization is valid and unrevoked; anything else waits for you. Bugs go back to the agent that made the change. Exceeding the cost or time budget, or a loop cap, parks the story and asks you, unless the project chose tripwire mode or turned budgets off. Builder questions go to the orchestrator; the orchestrator answers only what the spec settles, citing the clause, and brings everything else to you. You may delegate bounded decision rights in writing; delegated decisions are logged with their clause and shown to you.

**Gate 4, acceptance of the product.** When the authorized plan is built and verified, a fresh-context agent writes the acceptance packet for the application, not for a story: a working preview you click through, a plain-language account of what was built, the requirements covered, the evidence from every executed check and recorded review, the delegated decisions, screenshots of the approved screens, what remains uncertain or unfinished, and four closing lines: what changed, what was checked, what remains uncertain, what your approval authorizes. Engineers also get the diff. You are deciding whether the product delivers the approved experience, and you accept or reject with reasons. Acceptance is yours: no agent writes it and it cannot be delegated.

**Gate 5, release.** The release candidate is built and verified first. The checklist binds the exact revision, artifact, environment, configuration and migrations, with evidence for each item, a rehearsed rollback, and the security condition: every story's scans and security review complete, no unresolved blocking finding, every exception a visible waiver. You sign off on the release and its rollback together; authorization to build was never authorization to deploy. A release agent then deploys exactly that artifact through an executor that holds the credentials, so no model ever sees them. A confirmed smoke-test failure triggers the pre-approved rollback at once; any other recovery waits for you.

**Throughout.** State lives in files, so any session can restart. Approvals, locks and decisions are records a human wrote or a checked process produced; agents cannot write them. Inside Orca, the board's columns are the workflow stages, commands approve and answer from a human-owned shell, and notifications reach you when something needs you. Metrics report issues caught per gate, bugs that reached production, rework, and time and tokens per story. The workflow does not measure how you review or approve. A retrospective offers one optional question per release and proposes rule changes as a pull request you approve.

## 3. What the first usable release must do

**Milestone zero**, the exit of phase one, is one story end to end on a single Claude Code session: requirements, locked tests, implementation, evidence, a human-approved merge, and recovery after killing the session at any point, with a changed locked test, a stale approval and unsupported evidence all exercised and refused. Automatic merging is disabled in milestone zero: every pull request to main needs your approval record, deliberately, because milestone zero is the experiment that proves the approval path itself. Authorized execution, the recorded code review and product acceptance arrive with phase 1b, which completes the sequential workflow before any parallel execution.

**Version one**, in order:

1. Phase one: gates 1 to 4 on the inline backend, the approval path, locks, traceability, the build plan, the QA loop, and milestone zero.
2. The Orca backend: supervised parallel builders, the board, and bugs routed back to the same worker.
3. Gate 5 and the release executor.
4. The Orca control room, metrics and the retrospective.
5. Phase two: managed setup of git, the remote, CI, branch protection, hooks and the keychain flow.

The first project built this way is pod-factory itself, under a declared bootstrap exception until its first release ships.

**The reference application**, built in phase 1b, is the second project and demonstrates what pod-factory cannot demonstrate on itself: a database-backed journey through an approved mockup, with sign-in, a list and a detail view that one role may edit and another may only read, each screen's loading, empty and error states, and the production checks the contract names. It is deliberately small: one journey, two roles, one table, no feature beyond what those criteria need. It is a separate project in the repository, built through the workflow like any other, and it is not part of the pod-factory product surface.

## 4. Observable acceptance criteria

Grouped by requirement ID. Each criterion is observable: a block, a recorded result, or a recorded review. Verification evidence is produced by the test harness, CI, or the factory executor and bound to the content tested; an agent's claim that a check passed is not verification evidence. A recorded review is evidence that a named reviewer examined bound content and what it found, never evidence that a check passed. The tech spec maps every criterion to one of those kinds and supplies the mechanisms.

**REQ-01 Start.** A PRD draft, a project profile and project rules exist after the interview. Product questions cannot be skipped; technical defaults are recorded. Creating application code while gate 1 is open is blocked. The preflight names every enforcement layer as present or missing, and gate 1 cannot close with one missing unless a waiver is recorded.

**REQ-02 Discover.** The discovery report has conventions, measured coverage, risky areas, vulnerable dependencies and proposed rules, contains no secrets, proposes only additions to the project rules with any proposal to change existing code flagged as out of scope, and must be approved before design in an existing codebase.

**REQ-03 Gate 1.** Approval is given through the approval path and binds the PRD by requirement and the mockup. Design refuses to start without a matching record. Every red-team role reports findings or "none found"; undispositioned findings and unacknowledged dismissals block approval. A revocation reopens the gate.

**REQ-04 Design.** The design has every required section, including the threat review, production readiness and the criterion-to-control mapping. Every requirement appears in a phase. Every significant decision records who decided: you, a delegated category, a recorded default, or a cited clause; a decision record that both cites a settling clause and records a question put to you is rejected; which clauses settle a question is reviewed, not measured. The design states the project's production requirements and its production readiness criteria with their thresholds: security, performance, configuration, migrations, observability, deployment and recovery. Ordinary technical choices resolved inside the approved constraints are recorded as defaults with their reason, and the decisions left for the approver arrive in one consolidated review. Without an engineer on the project, a technical review is attached before approval, written by a reviewer whose recorded inputs are exactly the inputs named for that role and whose session started for that task.

**REQ-05 Eval plan.** Every requirement has positive and negative tests tagged with its ID and a regenerated plain-English rendering you acknowledge. Before the approval that locks it, each test is classified: new-behavior tests fail for the expected reason, negative tests are paired with the positive operation they guard and the pair demonstrates the missing behavior, existing tests keep their baseline; anything else blocks that approval by name. Every approved journey has at least one end-to-end test, covering its failure and permission cases. AI features carry safety thresholds of 100 percent of their defined scenario set. Coverage is stated as named tests against named criteria, journeys, business rules and permission rules, never as a line-coverage percentage; every threshold in the contract is a number or a named level, and no threshold is stated as an absence of defects.

**REQ-06 Gate 2 and the build contract.** Approval binds the contract: the requirements and scope, the mockup and its interaction behavior, the significant architecture decisions and boundaries, the acceptance criteria and test plan, the eval plan, the runbook, and the production readiness criteria with their thresholds. The lock covers the tests, the eval plan, runner configuration, fixtures, the exact test command, lockfiles, smoke tests, runbook scripts and the enforcement code. Tests arrive per phase; each phase's tests join the lock through a human-written amendment before that phase's build plan. An agent edit to a locked path is denied; a commit changing one without a human-written amendment fails before merge; CI runs the locked command, not the branch's. Amendments show before-and-after renderings you acknowledge. Agents may add tests where the locked runner configuration already includes them, beside the code they test and inside their story's approved scope, and such a test never stands in for an approved acceptance test; which paths the runner collects is itself locked, so no agent widens or narrows the set; an agent edit that weakens an approved acceptance criterion is denied as a locked-path change.

**REQ-07 Gate 3 and authorization.** Every story carries requirement and test IDs, interfaces, file scope, budgets, caps, agent and model, its dependencies and the stories it may run alongside; shared foundations come first, and at most two builders run at once by default. The gap report covers every check; undispositioned findings block approval. The packet states estimated tokens and days. Every story cites the approved requirement it serves or the technical dependency it justifies, and a story citing neither blocks the plan. No story is dispatched without a matching record, and a story cannot start until it is ready. The approval authorizes agents to execute that plan: stories are created, implemented, reviewed, verified, corrected and progressed with no further human record, and no agent widens that authority or writes itself another.

**REQ-08 Build.** A story is done when the part of the contract it carries is met: its acceptance tests pass on its branch, its recorded review is closed with no open blocking finding, and nothing in its diff lies outside its approved scope. Passing tests alone is not done, and behavior the contract does not carry is reported by name and removed, not accepted. Each builder session leaves a handoff note. The inputs the orchestrator supplies to a builder are recorded with their hashes and limited to the story file, the spec sections and mockup screenshots it lists, and the project rules; what a builder reads afterwards with its own tools is outside the record until sandboxes exist. Builders hold no deploy credentials, and a diff outside the story's file scope fails. Killing the builder, the orchestrator or Orca at each defined kill point (after every record write, between steps, during a record write, during a push) and restarting loses no record and duplicates none.

**REQ-09 Verify.** A story cannot merge with a failing check, an unresolved blocking security finding, or QA without evidence. Untraced code is reported by path. Fixes go to the originating worker. The combined application is verified on main's own tree after every merge, and progression waits for a passing result for main's current tree: a failing, missing, pending or earlier-tree result stops new work and further merges. When that verification fails, the story whose merge produced the failing tree is resumed for a bounded repair inside its own approved scope, by the worker that built it and even when that story is already done, while every unrelated story stays blocked; a repair that needs a path outside that scope, or that leaves the failure in place a second time, goes to the human. Budget and cap overruns park the story, flag it when the project chose tripwire mode, or do nothing when the project turned budgets off; every packet and the status page show which mode is active. Artifacts are redacted before they are written.

**REQ-10 Merges and gate 4.** An implementation merge without a human approval record happens only when a CI-validated authorization covers the story, every required check passes for the exact content being merged, that content's recorded review is closed with no open blocking finding, and the diff stays inside the approved file scope. The content merged automatically is the candidate that includes main as it stands at that moment, so when main moves the candidate is refreshed and its checks and its review run again, and no automatic merge rests on a result for content that is not what would land. Anything outside an authorized story's scope needs a human record, and a revoked authorization blocks every pull request relying on it. A content change after a review requires a new review. Acceptance of the product is a human record bound to the accepted revision and its evidence; the packet is written from the final content by a reviewer whose recorded inputs are exactly the inputs named for that role and whose session started for that task, contains every section, ends with the four closing lines, and the summary contains no code. Acceptance is never delegated.

**REQ-11 Gate 5.** The artifact is built and verified before sign-off. Every checklist item has evidence, including the rollback rehearsal and the security condition. Sign-off binds revision, artifact digest, environment, configuration, migrations, runbook and rollback plan.

**REQ-12 Orca control room.** Board columns match story stages. Every open gate and question appears on the status page and raises a notification. Approving from Orca produces the same record as the CLI, and the approving process refuses to run from a known agent session and runs only from a human-owned shell; an agent forging a record as your user is the accepted limitation in section 5.

**REQ-13 Escalation.** Under Claude Code, a dispatched builder's attempt to open the local question tool is denied and pointed at the orchestrator's ask command; other agents are held by instruction only. Every decision is logged with date, decider and outcome; orchestrator decisions carry the clause relied on. Between orchestrator and human, the needs-human flag clears only through your answer record; no timeout and no agent action clears it. A gap found during implementation pauses the affected work, states the consequence and proposes the smallest amendment, while independent work continues; no agent invents product behavior or changes the contract.

**REQ-14 Metrics.** Issues caught per gate, production bugs from incident records, rework rate, and time and tokens per story, computed from records with no network access. Story time is elapsed time, not effort.

**REQ-15 Retrospective.** Proposed rules cite the failure that motivated them and are applied only on approval. The feedback question is optional and never a gate.

**REQ-16 Install.** Skills install with one command; the Claude Code plugin adds hooks and commands; the Orca entry is labeled experimental; the whole workflow runs with Claude Code alone, demonstrated by the scripted flow in CI and by the live milestone-zero run.

**REQ-17 Delegation.** Only a written policy grants authority, by category, and with none every gate waits for you. Every delegated decision cites its category and clause or is rejected as a question that should have been asked. Bounded decision rights during build are the only thing delegable, and conditions are checked from evidence; the build contract, product acceptance and release sign-off are never delegated, and no agent writes a delegation or widens one.

**REQ-18 Release execution.** The release refuses to start without a validated sign-off matching every bound input. A rebuild that does not reproduce the approved digest halts. A confirmed smoke failure rolls back without a human; a probe error never does; no other recovery runs without you. Planted canary credentials appear in none of the logs, artifacts, records, reports or executor output produced by the scripted release runs. Release state survives a crash.

**REQ-19 Operations.** `status`, `explain` and `doctor` exist; `doctor` fails when any enforcement layer is missing or waived; an event log and an audit view cover every record.

**REQ-20 Upgrades.** Records carry schema and factory versions; a migration command has tests; the enforcing version is pinned per project; an upgrade is a human-written amendment.

**REQ-21 Credentials.** Deployment credentials enter only through a hidden prompt, the keychain or a secret manager, and planted canary credentials appear in none of the transcripts, logs, artifacts, records or reports produced by the scripted story and release runs. Agent reads of declared secret files through file tools are denied; shell reads are denied by an advisory heuristic; the canary tests are the proof.

**REQ-22 Exceptions.** Revocations, human-written amendments and time-boxed waivers exist as records, every active waiver is visible on every packet, and each of the nine catalogued stop points (refused approval, blocked merge, parked story, halted release, failed rollback, lease expiry, invalid record, a hook denial that stops a builder, a failing doctor) and any unexpected crash produce a plain-language message with your options, checked by the plain-language lint, with the raw error kept in the log. A revocation shows as pending until CI confirms that every affected open pull request is blocked; the command never claims enforcement before that; validation is triggered at once with a schedule as the fallback, and a stale check cannot restore an obsolete green result.

**REQ-23 Mockup.** Every user-facing flow has a reachable screen, with its loading, empty and error states shown, or gate 1 blocks. The mockup lives apart from application code, builders see only its screenshots, and it is archived after gate 2.

**REQ-24 Managed setup (phase two).** After setup on a supported host and plan, `doctor` passes with no waiver; on an unsupported plan the setup offers public, upgrade or a visible waiver; setup is idempotent and never prints a credential.

**REQ-25 Environment setup.** Setup detects whether Docker is installed and running. When the design chose containers and Docker is available, it prepares the Dockerfile, the Compose configuration, startup commands and health checks; when Docker is unavailable it offers installation help or a supported local setup; the chosen mode is recorded and reused by every later agent; a previously working environment that fails is diagnosed, never silently switched. The local setup keeps the same application architecture, database engine, runtime versions, dependency lockfiles, migrations and configuration names as deployment, and never substitutes SQLite for Postgres. When the deployment target is containers, CI builds and tests the deployment image even if the developer runs locally without Docker, and deployment approval binds that artifact. Parallel builders get separate ports and test databases, and with Compose distinct project names and volumes per story; cleanup touches only that story's resources. The agent prepares configuration and performs authorized setup; the user completes any operating-system prompts.

**REQ-26 Pre-build gap review.** One review reads the PRD, the mockup and the architecture together before the build contract is approved, and reports by name every gap in the user journeys, business rules, permissions, integrations, responsive behavior, accessibility and loading, empty and error states, and in the production requirements: security, performance, configuration, migrations, observability, deployment and recovery. Each finding is blocking, deferred or dismissed with a reason the approver acknowledges, and an open blocking finding blocks the approval by name.

**REQ-27 Product verification.** Before the product is presented for acceptance, every approved journey has a passing end-to-end run including its failure and permission cases; the approved screens have a recorded browser review against the mockup and the approved interaction behavior, its screenshots in the evidence bundle and its record naming the revision reviewed; business rules and system boundaries have unit and integration tests; the security, accessibility, performance and operational checks the contract names have run against the thresholds it states; and the deployment artifact has been built and exercised in its intended environment. Each result is an executed check or a recorded review bound to the content tested, and recording it never changes that content. A failure is fixed inside the approved scope and the affected verification runs again. Verification is measured against the contract's stated coverage and thresholds, never against every possible condition.

## 5. Limitations and deferred capabilities

Stated for adopters.

- A deliberately malicious agent running as your operating-system user could forge a file-based approval. Version one guards against agent drift and mistakes, not against that; signatures are optional. A physical-action approval path is version two.
- Agent hooks are Claude Code only; Codex and other agents are held by pre-commit, CI and branch protection. Codex has the same hook events, and parity is a version-two candidate.
- Verification is measured against the coverage and thresholds the contract states, so the workflow does not promise a defect-free product; what it promises is that the stated checks ran against the content being accepted.
- Secrets outside the supported channels and declared paths are protected only by redaction patterns.
- On GitHub Free, private repositories have no server-side branch protection; such projects run under a visible waiver or upgrade the plan.
- Orca's orchestration and plugin system are experimental; the workflow never depends on them for enforcement, and a rich Orca side panel waits on capabilities Orca does not yet expose.
- In milestone zero, revocation is asynchronous: a pull request already green can stay mergeable for up to one validation interval; the revoke command shows pending until CI confirms the block.
- Deferred to version two or later: per-story sandboxes, physical-action approvals, production evals and monitoring of AI features, mutation testing, feature flags beyond a recipe, hosted or multi-user service, Jira and Linear sync, the control room on SSH worktrees, high-fidelity design tooling. Provisioning hosting or cloud accounts is out of scope.
